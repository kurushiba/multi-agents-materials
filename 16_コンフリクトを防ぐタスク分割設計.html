Theoryコンフリクトを起こさないタスク分割設計論

  • Worktreeが防ぐ競合の本質

    Git Worktreeは、あくまで「ローカルでの開発作業中にファイルシステム上で競合してしまうこと」を防ぐ技術です。

  • 最終マージ時のコンフリクト

    メインブランチへ並列作業を統合する（マージする）際の、Gitコンフリクト自体を自動で解決してくれるわけではありません。

  • 事前設計こそが最大のマージ対策

    AI並列開発 of 恩恵を最大化するには、AIにタスクを渡す前に人間が「コンフリクトを未然に防ぐタスク設計」をする必要があります。

📂
Git Worktree
作業中の物理的な競合を防ぐ
ローカルフォルダの分離で別タスクを快適に同時実行
AND
🧠
人間によるタスク設計
統合時の論理的な競合を防ぐ
事前のタスク分割設計でマージ時のコンフリクトを回避

Principle 1原則①：ファイル所有権で分割する

  • 機能の概念だけでの分割は危険

    「ログイン機能」と「パスワード変更」のように機能単位だけで切り分けると、共通ファイルへの同時書き込みが発生しやすくなります。

  • 共通ファイルの編集競合

    共通UIコンポーネント、ルーター、設定ファイルなどを複数のAIが同時に編集すると、激しいコンフリクトが発生します。

  • ファイル所有権に基づくアサイン

    「どのファイルを読み書きするか」を基準にタスクを分割し、各AIが触る範囲が重複しないよう設計します。

Principle 2原則②：依存し合う機能は並列にしない

  • 相互依存する開発タスクの禁止

    互いに密接に依存し合っている開発タスクは、絶対に同時に起動してはいけません。

  • スキーマ定義とAPI実装の例

    「DBテーブル定義の追加」と「そのテーブルを利用するAPI実装」を並列化すると、未定義のテーブルへのテストが走りクラッシュします。

  • 直列化による安全な順序制御

    先行するタスク（スキーマ定義）を完全に完了させ、メインに統合してから、後続のタスク（API実装）を開始します。

Principle 3原則③：Worktreeは短命にする

  • ライフサイクルを短く回す

    Worktreeは、「作る ➔ 作業する ➔ マージする ➔ 削除する」という一連のライフサイクルを、できるだけ短期間で回します。

  • 本流からの乖離によるリスク

    放置された古いWorktreeはメインの本流から乖離し、いざマージしようとした時に巨大なコンフリクトを引き起こします。

  • AIの「古い前提」でのミスを防ぐ

    AIエージェントに古いコード前提のまま作業を続けさせると、不必要なエラーや論理的な設計ミスが発生しやすくなります。

🔄 短サイクル開発のメリット 本流との乖離を最小限にし、AIの間違いとマージの手戻りを防止

Summaryまとめ：並列開発の3つの設計原則

  • ファイル所有権によるタスク分割

    機能だけでなく、触るファイルが重複しないようにアサインを切り分ける。

  • 依存する機能の直列化

    スキーマの変更など、他が依存する先行タスクはメインに統合してから次へ進む。

  • 短命なWorktreeの徹底

    「作成から削除まで」を素早く完了させ、古い情報での手戻りを防ぐ。
